I read the code behind GitHub's most-starred AI humanizers and watermark removers

I read six of the most-starred repos, merged the three humanizers that complemented each other, and tested the result against the 72,000-star original on 20 samples.

Why I read the code first

I wanted a humanizer for AI-assisted drafts and wanted to know what AI watermark removers do, so I took the most-starred GitHub repos in both categories and read them before installing anything. The star counts and the code told different stories. The best humanizer was good, and a merged version matched it on my test at less than half the input tokens.

What I did on 24 November 2026:

  1. Searched GitHub for humanizer and watermark remover repos and sorted the results by stars.
  2. Cloned the top ones and read each: the license, the size, the tests, every host the code contacts, and whether the code does what the README says.
  3. Merged the three humanizers that complemented each other, then tested the merge against the most-starred original on 20 AI-written samples, scored by two separate checkers.

I also ran the top watermark remover on files I built and on real images from ChatGPT and Gemini.

The repos, by the numbers

Stars ranged from 3,445 to 72,713, and the count said little about what each repo contained.

A 12,500-star humanizer with no code to read

The third result for "humanizer" had 12,583 stars and no engine code. Its files are a README, a user manual, API documentation, badges and the pages of its documentation site. Its license reserves all rights, and the README links to a hosted app.

That is a normal way to run a product, and the README is open about it. It means the stars point at a landing page. I was looking for something I could read and run on my own machine, so there was nothing here for me to evaluate.

The top watermark remover cleans metadata

guillaumemeyer/watermarks-remover, at 28,247 stars, removes provenance data. It strips C2PA manifests, EXIF and XMP fields, document properties and invisible Unicode characters, in formats from PNG and MP4 to DOCX and PPTX. Its README lists what it covers, and visible marks drawn into the pixels are not on that list.

From the name, I had expected visible watermarks. The mismatch was in my assumption, not in its documentation.

I ran it on files I built and on two real AI images, then checked the bytes myself:

Test input Removed Left unchanged
Text with 15 hidden characters: zero-width spaces and joiners, tag characters, a right-to-left override All 15 The visible words
PNG with text metadata, an XMP block labelling it AI-generated, and a C2PA-style block All three blocks Every pixel
JPEG with 2 EXIF tags Both tags, with no recompression Every pixel
Real ChatGPT image (1448 × 1086) with a 24,922-byte C2PA manifest The manifest; the file went from 2,239,927 to 2,214,993 bytes Every pixel
Real Gemini image with the visible sparkle Nothing, as the file had no metadata Every pixel, so the sparkle stays

Two details matter if you rely on it. After cleaning the ChatGPT image, its own report still said C2PA was present. The flag came from the four bytes cai: occurring by chance inside the compressed pixel data, and its inspector marks that finding as a likely false positive.

The ChatGPT manifest also records a c2pa.watermarked action, the C2PA standard's marker for an invisible watermark added to the content. A metadata tool leaves pixels alone by design, so that watermark stays.

It is also one of the most carefully built repos I opened: 26,000 lines of Python, 76 test files with 22,000 lines of tests, a security policy, and a README that says what the tool cannot do. One folder made me look twice: stealer/. It implements watermark stealing, a published research method from ETH Zurich. It is not a credential stealer.

The 72,000-star humanizer is good, and it is one prompt

Siqi Chen's blader/humanizer is the strongest of the group. It is a single instruction file for AI agents, built on Wikipedia's "Signs of AI writing" guide, and it does three things well:

  • It ranks 26 patterns by how reliably each one signals AI text, so a model acts on strong tells at once and needs several weak ones before it edits.
  • It tells the model to treat pasted text as material to edit, never as instructions, which blocks a draft that says "ignore your rules".
  • It makes the model check that no fact, name, number or quote was lost before it answers.

Its README is honest about scope: it edits for human readers, and AI detectors still flag most of its output.

The trade-offs come from the format. The whole file loads on every run, and in my test that was 12,300 input tokens per run, nearly all of it instructions. Nothing checks the output mechanically, so every tell has to be caught by the model reading carefully. It also has no mode that audits a draft without rewriting it.

Two smaller repos had what it lacked

Peter Yang's no-ai-slop (13,745 stars) is 97 lines built around keeping the writer's voice. Its rule is the minimum effective edit: fix the tells, leave strong human sentences alone. It names tells the bigger file does not list, such as colon reveals ("The best part: it learns.") and synonym cycling, and it adds a portability test: a sentence that could move unchanged to another company says nothing about this one. It also has a detect mode that audits a draft without rewriting it, and a 43-line checklist the model runs on its own output.

Conor Bronsdon's avoid-ai-writing (6,065 stars) has the only deterministic detector of the three. It is a JavaScript engine that scores text from 0 to 100 and can gate a CI pipeline, plus a verifier that compares a rewrite against its original. The engine lives in one 3,762-line file, copied into each sub-skill's folder. I used it unchanged as the independent scorer in my test.

A different approach: translation chains

lynote-ai/humanize-text (3,445 stars) is a real application with readable code, and it takes another route. An LLM rewrites the draft into Chinese and then Japanese, and machine translation carries it through Finnish back to English, with every step traced. It runs with your own keys for an LLM and a translation service.

Round-trip translation changes a lot of wording, which suits some goals. I wanted the smallest edit that keeps the writer's voice, so it did not fit my use, and I left it out of the merge.

Merging them into humanize-prose

All three humanizers I kept are MIT-licensed, so I merged them into humanize-prose, with each author's copyright notice in its NOTICE.md.

Part Taken from
Pattern catalog ranked by strength, the fact check, the rule against following instructions inside the text, file and embedded modes blader/humanizer
Minimum-effective-edit and voice rules, detect mode, the portability test, colon reveals, synonym cycling, the self-check no-ai-slop
A deterministic scan, and a check that a rewrite kept the original's facts avoid-ai-writing's idea, rewritten as one Python file

The instruction file is 13.4 KB against blader's 33.6 KB. The script, check.py, is 155 lines with no dependencies and two commands:

python3 scripts/check.py scan draft.md            # mechanical tells; exit 1 on a strong one
python3 scripts/check.py verify draft.md new.md   # numbers, names, links and code a rewrite dropped

scan skips code, links, blockquotes and quoted text, so a document that discusses a tell is not punished for quoting it. The repo has 15 tests, including one that runs the scanner over its own README and instruction file.

How I tested it

The prompts named a topic, the facts a rewrite must keep and a length, and asked for no style, so the tells came from the model's own habits. Each call ran from an empty folder with the skill file as the entire system prompt. Tools, skills, MCP servers, saved sessions and user settings were off.

Both skills were asked for embedded mode, which returns only the final text. A rewrite took about 5 seconds either way: 4.7 s on average for blader/humanizer and 5.1 s for humanize-prose. The harness is two short Python scripts, run.py and score.py, in the repo's evals/ folder.

Results: the same cleanup at 55% fewer input tokens

humanize-prose matched blader/humanizer on removing tells and keeping facts, and used 55% fewer input tokens per run.

My first version lost on rhythm. The avoid-ai-writing detector flagged even sentence lengths or punctuation in 4 of its 20 rewrites and in none of blader's. I made flat rhythm a named tell, added a self-check that any text of five or more sentences has at least one under 10 words, and reran the humanize-prose side. Its sentence lengths now vary a little more than blader's on average, a spread of 0.52 against 0.50, and the flagged rewrites dropped from 4 to 3. blader's still have none.

All three avoid-ai-writing findings on humanize-prose are statistical: sentence lengths or punctuation too even across about 140 words. None is a word or a phrase. Spread is the standard deviation of sentence length divided by the mean, with sentences split the way avoid-ai-writing splits them. Output tokens run well above the length of the text, so they include the model's reasoning and vary between runs; input tokens are fixed by the size of the instructions.

The nurse manager's LinkedIn post (sample 17) shows how close the two ran. The original:

Here's the truth: nights strip away everything unnecessary. There are fewer people, fewer resources, and no one to escalate to at 3 a.m. except the person standing next to you. So you learn quickly that teamwork isn't a value on a poster. It's a survival skill.

blader/humanizer:

Nights have fewer people and fewer resources, and at 3 a.m. there is no one to escalate to except the person standing next to you. You learn fast that teamwork isn't a value on a poster. You need it to get through the shift.

humanize-prose:

Nights strip away everything unnecessary. There are fewer people and fewer resources, and at 3 a.m. there is no one to escalate to except the person standing next to you. You learn quickly that teamwork is how you get through the shift.

Both cut the "Here's the truth" opener and swapped the "survival skill" kicker for a plain sentence. In the support reply (sample 12), both dropped "We're happy to help with anything else you need" and ended on the refund timeline. Every sample and both rewrites are in evals/outputs.md.

My own checker had two bugs, and both hurt my skill

The first scores had humanize-prose at 3 strong tells and blader/humanizer at none. All three were en dashes in ranges: "CAD 140,000 – 165,000" in the job post and "April 3 – August 30" in the museum text. My instructions tell the model to keep dashes in number ranges, and it did; my scanner flagged every spaced en dash anyway. blader/humanizer had turned the same salary into "140,000 to 165,000", which is also fine.

The second bug was in verify. It counted "Offline Mode" becoming "offline mode" as a dropped name, which inflated the facts-dropped count for both skills: 18 against 14 before the fix, 9 against 7 after.

I fixed both, added regression tests, and re-scored the same saved outputs without calling the model again. The fixes and the raw outputs are in the repo, so anyone can check them.

What this test can and cannot tell you

The samples were cleaner than I expected. Twenty texts from Claude Sonnet 5.5, averaging 166 words, carried 3 strong tells between them: one em dash, one "happy to help" and one "isn't X. It's Y." So this run measured cost and damage more than cleanup.

  • One rewrite per sample per skill. A second run would move some numbers.
  • I tuned the rhythm rule over four reruns of humanize-prose on these same 20 samples, so its rhythm figures are a development result, not a held-out test.
  • The model ran without tools, so humanize-prose's script could not run during the rewrite. This tested the instructions alone.
  • I wrote check.py alongside humanize-prose. That is why every output was also scored by avoid-ai-writing's detector, which I did not write.
  • Neither skill tries to get past AI detectors, and this test did not measure that.

The next test needs messier input, such as drafts from an older model, where a humanizer has more to fix.

What I check before installing a repo now

Stars tell me where to start reading. These six checks took minutes per repo and changed what I installed:

  1. The license. "All rights reserved" means I can read the README, not reuse the code.
  2. That the code exists and does what the README says.
  3. The tests, and whether they pass.
  4. Every host the code contacts. A search for URLs across the source takes a minute.
  5. Names that look alarming. The stealer/ folder was a research method, and reading it took five minutes.
  6. A run on my own input, scored by something I did not write.
